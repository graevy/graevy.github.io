Introduction

The only real k8s cli tool and frequent sysadmin cluster entrypoint, kubectl offers the get subcommand to “Display one or many resources” in a cluster. All kubernetes resources live in a namespace, have a type, and can be represented as text2. Because kubernetes clusters are very stateful3, and tend to involve multiple people, enumerating namespace contents is a helpful feature, especially for newer users absorbing information.

kubectl get all is a legacy subcommand. Peek under the hood if you want. Kubernetes documentation no longer mentions kubectl get all under kubectl get because of…conflict. Please, dear reader, experience:

Chaser

kubectl delete --all does not include uninitialized resources4

kgetall

After staring at this xargs incantation I did eventually osmotically grasp that it does a k8s-apiserver get (with the auth and api discovery overhead) for each resource type. This is much faster:

kgetall() {
  kubectl get $(kubectl api-resources --verbs=list --namespaced -o name | grep -iv "^events" | paste -sd,) --show-kind --ignore-not-found "$@"
}

due to constructing a comma-separated list5 of resource types to grab in a single kubectl get. Currently I’m excluding events (which feel more debug-y than stateful) and usually passing -A for all namespaces.

When I organically encountered the edge cases of kubectl delete I also eventually wrote

kkill() {
	if [[ $# -eq 2 ]]; then
        # case: cluster-wide non-namespaced resource 
		kubectl patch $1 $2 --type merge -p '{"metadata":{"finalizers":null}}'
	else
		kubectl -n $1 patch $2 $3 --type merge -p '{"metadata":{"finalizers":null}}'
	fi
}

which, while sloppier due to modality, and rarely used, I am also a little chuffed about.

I have one poignant thing to say on this topic

Codebase warts are funny. Every footgun has a story; too awkward to maintain, too load-bearing to remove. When enough of these accumulate, a software project develops a reputation for inaccessibility6. I’m sure kubernetes people (kubers?) have a series of perfectly valid reasons for all not meaning all, but the cumulative effect seems indefensible.

New users want to see all so they can learn. Eventually, they learn more precise troubleshooting7, so the UX pattern becomes stackoverflow’s “being told not to do what you’re trying to do”. Haunting these github issues, I see its shape: established users undervalue doing things incorrectly. Computer touchers consequently bias against tool learnability, probably due to our familiarity with silicate geochemistry, but also maybe our meritocracy. Neither the machine interfaces we work in8, nor the systems that employ us, prioritize our accommodation or accessibility. Left unchecked, why would our tooling?
