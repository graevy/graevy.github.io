What

kubectl, the only real k8s cli tool and frequent sysadmin cluster entrypoint, offers the get subcommand to “Display one or many resources” in a cluster. All kubernetes resources live in a namespace, have a type, and can be represented as text1. Because kubernetes clusters are very stateful2, and tend to involve multiple people, enumerating the contents of a namespace (or all namespaces) is a helpful feature, especially for newer users, who might want to be peeking under the hood.

Kubernetes documentation doesn’t actually mention kubectl get all under kubectl get at the time of writing. I will say no more. Peek under the hood if you want.

Chaser:

kubectl delete --all does not include uninitialized resources

kgetall

After staring at this xargs incantation I did eventually osmotically grasp that it does a k8s-apiserver get (with the auth and api discovery overhead) for each resource type. This is much faster:

kgetall() {
  kubectl get $(kubectl api-resources --verbs=list --namespaced -o name | grep -iv "^events" | paste -sd,) --show-kind --ignore-not-found "$@"
}

due to constructing a comma-separated list3 of resource types to grab in a single kubectl get. Currently I’m excluding events (which feel more debug-y than stateful) and usually passing -A for all namespaces.

When I organically encountered the edge cases of kubectl delete I also eventually wrote

kkill() {
	if [[ $# -eq 2 ]]; then
      # case: cluster-wide non-namespaced resource 
		kubectl patch $1 $2 --type merge -p '{"metadata":{"finalizers":null}}'
	else
		kubectl -n $1 patch $2 $3 --type merge -p '{"metadata":{"finalizers":null}}'
	fi
}

which, while sloppier due to modality, and rarely used, I am also a little chuffed about.
